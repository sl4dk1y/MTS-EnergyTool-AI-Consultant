# Совместная разработка

Спасибо за вклад в MTS EnergyTool AI Consultant. Основной язык описаний, комментариев к изменениям, коммитов и Pull Request — русский.

## Ветки и Pull Request

- `main` — стабильная интеграционная ветка. Изменения в неё включаются через Pull Request.
- Для каждой самостоятельной задачи создавайте отдельную ветку от актуальной `main`.
- Используйте префикс по типу задачи: `feature/`, `fix/`, `docs/`, `refactor/` или `test/`, затем краткое имя латиницей, например `feature/session-history`.
- Не отправляйте изменения напрямую в `main`. Не выполняйте force push в `main` и не изменяйте чужие рабочие ветки без предварительного согласования с их автором.
- Перед открытием или слиянием Pull Request синхронизируйте свою ветку с актуальной `main`.
- Pull Request должен описывать задачу и сделанные изменения, содержать ссылку на связанную Issue (если она есть), проведённые проверки и известные ограничения. Отдельно укажите влияние на архитектуру и API, а также подтвердите проверку на секреты и закрытые данные.
- Просите ревью у другого участника команды, когда это возможно. Не включайте изменения в `main`, пока не устранены замечания ревью и конфликты слияния.

## Коммиты

Пишите сообщения коммитов на русском языке: коротко, по существу, с действием. Например: `Добавлена изоляция сессий` или `Исправлен формат ответа API`.

Перед коммитом просмотрите `git status` и полный staged diff. Убедитесь, что в нём только файлы задачи, нет `.env`, ключей, пользовательских данных, базы знаний МТС, примеров с закрытым содержимым и производных индексов.

## Контракты компонентов

Изменения общих контрактов между RAG, Agent и Backend предварительно согласовывайте с командой. В описании Pull Request перечисляйте затронутые форматы данных, интерфейсы и совместимость компонентов.

## Merge conflicts

1. Обновите ветку из актуальной `main` обычным merge или согласованным с командой способом.
2. Разберите каждый конфликт с авторами затронутых изменений, если смысл правок неоднозначен.
3. Не удаляйте чужие изменения только ради устранения конфликта.
4. Повторите релевантные проверки и укажите разрешение конфликтов в Pull Request.

## Материалы организаторов

Материалы МТС и организаторов используйте только для выполнения задания. Не добавляйте в Git исходную базу знаний, её копии или производные, закрытые тестовые вопросы и ответы, регламент, архивы исходных материалов, индексы с закрытым содержимым или другие материалы, публикация которых не разрешена. Храните их локально; перед коммитом проверяйте `git status`, `git check-ignore` и staged diff.

## Защита ветки `main`

Рекомендуемые настройки GitHub:

- требовать Pull Request для слияния в `main`;
- требовать одно одобрение другого участника, когда это возможно;
- запрещать force push и удаление `main`;
- после настройки CI сделать успешные CI-проверки обязательными для слияния.

Эти настройки должен включить владелец репозитория вручную в GitHub. Настройки репозитория этим документом не меняются.
