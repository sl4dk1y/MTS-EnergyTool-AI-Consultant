# Совместная разработка

Пишите документацию, комментарии к изменениям, сообщения коммитов и описания Pull Request на русском языке.

## Ветки и Pull Request

- `main` — стабильная ветка проекта. Сливайте изменения в неё через Pull Request.
- Для каждой задачи создавайте отдельную ветку от актуальной `main`.
- Назовите ветку по типу работы: `feature/`, `fix/`, `docs/`, `refactor/` или `test/`, затем добавьте короткое имя на латинице. Например: `feature/session-history`.
- Не отправляйте коммиты прямо в `main` и не делайте туда force push. Не меняйте чужую рабочую ветку без согласования с её автором.
- Перед Pull Request обновите свою ветку от актуальной `main`.
- В Pull Request опишите задачу и изменения, приложите ссылку на Issue, если она есть, и перечислите выполненные проверки. Укажите влияние на архитектуру и API, известные ограничения и результат проверки на секреты и закрытые данные.
- Попросите другого участника проверить изменения, если это возможно. Перед слиянием разберите замечания и конфликты.

## Коммиты

Пишите короткие сообщения коммитов по-русски и называйте действие: `Добавлена изоляция сессий`, `Исправлен формат ответа API`.

Перед коммитом проверьте `git status` и весь staged diff. В нём должны быть только файлы задачи. Уберите `.env`, ключи, пользовательские данные, материалы МТС и индексы с закрытым содержимым.

## Контракты компонентов

Сначала согласуйте с командой изменения общих контрактов RAG, Agent и Backend. В Pull Request перечислите затронутые форматы данных и интерфейсы, а также укажите, сохраняется ли совместимость.

## Merge conflicts

1. Обновите ветку из актуальной `main` обычным merge или согласованным с командой способом.
2. Разберите каждый конфликт с авторами затронутых изменений, если смысл правок неоднозначен.
3. Не удаляйте чужие изменения только ради устранения конфликта.
4. Повторите релевантные проверки и укажите разрешение конфликтов в Pull Request.

## Материалы организаторов

Материалы МТС и организаторов используйте только для выполнения задания. Не добавляйте в Git исходную базу знаний, её копии или производные, закрытые тестовые вопросы и ответы, регламент, архивы исходных материалов, индексы с закрытым содержимым или другие материалы, публикация которых не разрешена. Храните их локально; перед коммитом проверяйте `git status`, `git check-ignore` и staged diff.

## Защита ветки `main`

Рекомендуемые настройки GitHub:

- требовать Pull Request для слияния в `main`;
- требовать одно одобрение другого участника, когда это возможно;
- запрещать force push и удаление `main`;
- после настройки CI сделать успешные CI-проверки обязательными для слияния.

Включить эти настройки должен владелец репозитория в GitHub.
