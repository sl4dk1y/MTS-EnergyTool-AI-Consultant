# RAG: поиск по базе знаний EnergyTool

Модуль `rag_engine.py` — гибридный поиск по базе знаний. Вызывается из
`consultant_engine.py` через протокол `Retriever`: объект с методом
`retrieve(query, top_k) -> list[RetrievedChunk]`.

## Место в цепочке

```text
solution.py  ->  consultant_engine.consult()  ->  RagRetriever.retrieve()
                     (промпт, история, отсев)        (чанки + source + score)
```

Подключение — одна строка в `build_default_engine`:

```python
from rag_engine import build_default_retriever

retriever = build_default_retriever()   # вместо KnowledgeBaseSearch.from_path
```

`build_default_retriever()` возвращает `None`, если база не найдена: движок
продолжает работать без контекста и честно отвечает, что данных нет.

## Контракт

Используется `RetrievedChunk` из `consultant_contracts.py` как есть:

```python
@dataclass(frozen=True)
class RetrievedChunk:
    text: str
    source: str
    score: Optional[float] = None
```

`source` — `путь/к/файлу.md > Раздел > Подраздел`, путь относительно корня
базы знаний (каталога или архива). Этот же текст движок показывает в режиме отладки веба.

`score` всегда положительный и сопоставимый по шкале. Относительное отсечение
задаётся на стороне Consultant Engine: по умолчанию `RELATIVE_SCORE_CUTOFF = 0.0`,
то есть отсечение выключено, пока движок не передаст ненулевое значение. RAG
применяет порог как есть и сам фрагменты не отбрасывает. Если отсечение
включат, плоские скоры (например, чистый RRF) станут бесполезны — поэтому
каналы объединяются нормированными значениями.

## Как устроен поиск

1. **Источник.** В `DATA_DIR` сначала ищется распакованный каталог
   `knowledge-base/` (также `knowledge_base/` или `kb/`), затем архив
   `knowledge-base.zip` или `knowledge_base.zip`. Проверяются также каталог
   рядом с модулем и рабочий каталог. Архив распаковывается во временную
   директорию с защитой от выхода за её пределы, один раз на процесс.
   Из каталога или архива загружаются файлы `.md` и `.txt`.
2. **Чанкинг.** Markdown режется по заголовкам `#`, `##`, `###`; иерархия
   заголовков уходит в `source`. Блок длиннее 3200 символов дробится по
   абзацам с перекрытием. Короткий хвост приклеивается к соседнему чанку
   только внутри одного раздела: чанки с разными `source` не объединяются,
   иначе текст получил бы чужой источник. Таблицы и списки не разрываются:
   разрезается только между строками.
3. **BM25.** Своя реализация, без зависимостей. Токенизация: нижний регистр,
   русские стоп-слова и усечение распространённых окончаний. Это помогает
   сопоставлять близкие словоформы; полноценная лемматизация потребовала бы
   дополнительной библиотеки.
4. **Эмбеддинги (необязательно).** `POST {LLM_BASE_URL}/embeddings` с моделью
   из `EMB_MODEL`, батчами по 32. Векторы нормализуются, косинус считается
   через numpy, если он установлен, иначе чистым Python. Фрагменты с
   косинусом ниже `DENSE_MIN_SIMILARITY` в объединение не попадают. Ошибка
   или таймаут эмбеддингов не роняет поиск: канал отключается на этот запрос,
   остаются результаты BM25.
5. **Объединение.** Скоры каналов нормируются и складываются с весами
   0,6 (BM25) и 0,4 (эмбеддинги). Нормировка выбрана вместо RRF: тогда скоры
   остаются сопоставимыми, если Consultant Engine включит относительное
   отсечение.
6. **Реранкер (необязательно).** Топ-15 кандидатов уходят в
   `POST {LLM_BASE_URL}/rerank` с моделью из `RERANKER_MODEL`. Логиты
   переводятся сигмоидой в `(0, 1)`. Ответ проверяется строго: число
   результатов должно совпадать с числом документов, индексы — целые, без
   дублей и в диапазоне, оценки — конечные числа. Любое нарушение означает,
   что реранкер не применяется и остаётся исходный порядок.
7. **Отказ.** Пустой запрос, пустая база, недоступная модель — возвращается
   пустой список, решение принимает движок.

### Порог векторного канала

`DENSE_MIN_SIMILARITY = 0.25` — минимальное косинусное сходство, при котором
фрагмент плотного канала допускается в выдачу. Без порога на посторонний
вопрос в контекст попадали бы случайные разделы базы, и модель могла бы
выдать их за ответ.

Калибровка: прогнать `tools/eval_retrieval.py` на размеченных вопросах и
поднимать порог, пока hit@1 не начнёт падать. Отдельно проверить, что на
заведомо посторонних вопросах (не про энергетику) выдача плотного канала
пустая. Значение вынесено в константу, а не в переменную окружения: платформа
его не передаёт, менять его на месте незачем.

### Отказ векторного канала

Если `_query_vector` или `_DenseIndex.search` выбросили исключение, поиск
продолжается на BM25: результаты лексического канала уже получены, и
обнулять всю выдачу из-за одного сетевого вызова нельзя. Ошибка пишется в
stderr, в выдаче остаются только лексические кандидаты. То же происходит,
если все плотные кандидаты оказались ниже порога.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` / `OPENAI_BASE_URL` | адрес прокси организаторов |
| `LLM_API_KEY` / `OPENAI_API_KEY` | служебный ключ, в логи не попадает |
| `EMB_MODEL` | модель эмбеддингов; без неё плотный канал выключен |
| `RERANKER_MODEL` | модель реранкера; без неё реранкер не вызывается |
| `TOP_K` | размер выдачи; по умолчанию 8 в Consultant Engine и 5 при прямом создании `RagRetriever` |
| `DATA_DIR` | каталог, в котором искать каталог базы или `knowledge-base.zip`; по умолчанию `data` |
| `RAG_DISABLE_DENSE` | `1` — принудительно работать только на BM25 |

`CHUNKER` и `RERANKER_TOP_N` платформа передаёт, но модуль их не использует:
размер чанка задан константами, число фрагментов определяет `TOP_K`, а
реранкер переставляет всех 15 кандидатов. Это осознанное упрощение.

## Потокобезопасность

`consult()` вызывается из нескольких потоков (`MAX_WORKERS`). Индекс
строится ровно один раз под `threading.Lock` (двойная проверка), дальше
`retrieve` только читает. Тест `test_thread_safety_builds_index_once`
проверяет, что при восьми параллельных вызовах база индексируется один раз.

## Сводка качества ответов

В предыдущем полном локальном прогоне обработаны 18 демонстрационных вопросов. В доступной сводке указано, что retrieval вернул контекст для всех 18 запросов, все 18 вызовов LLM завершились, ошибок API и fallback-ответов не было. Сформированы 18 непустых строк с сохранённым порядком ID. В отчёте были указаны общее время 245,59 с и среднее время вызова LLM около 8,2 с; медиана и хеш проверенной ревизии не сохранены.

Для сравнения с примерными ответами были посчитаны токеновые эвристики: средний F1 — 0,214, пересечение токенов ответа с переданным контекстом — 0,553. Эти значения не являются долей правильных ответов и не заменяют проверку фактов человеком. Доля подтверждённых утверждений и доля экспертно признанных корректными ответов не измерены.

Один ответ содержал числовое утверждение, которое не удалось найти в базе в явном виде. Сам ответ и его контекст не сохранились, поэтому происхождение числа — вычисление или неподтверждённая генерация — установить нельзя. Этот результат требует ручной проверки; число и содержание вопроса здесь не приводятся.

В дополнительном одиночном прогоне спорного сценария текущий BM25-поиск вернул контекст, а запрос Qwen завершился за 9,42 с без числовых утверждений. Это не подтверждает происхождение числа из предыдущего прогона и не является полной экспертной оценкой набора. Сводка предыдущего запуска не воспроизводится из текущей рабочей копии: подробные ответы, контекст и тайминги отсутствуют.

`tools/eval_retrieval.py` отдельно считает hit@k и MRR, но требует локальной разметки ожидаемых источников. Её результат оценивает только retrieval и не доказывает правильность сгенерированного ответа.

### Как запускать замер

```bash
python3 tools/eval_retrieval.py \
    --questions local-data/demo_questions.csv \
    --labels local-data/retrieval_labels.csv \
    --kb local-data/knowledge-base.zip \
    --retriever rag_engine:from_path
```

`--retriever` принимает `модуль:фабрика`, где фабрика получает путь к базе и
возвращает объект с методом `retrieve`. Поэтому указывается
`rag_engine:from_path`, а не `rag_engine:retrieve`: функция `retrieve` не
принимает путь к базе и не возвращает объект.

## Как запускать тесты

```bash
python -m unittest discover -s tests -p "test_rag.py" -v
```

CI использует `unittest`, а не pytest: `python -m unittest discover -s tests`.
Реальных запросов к прокси в тестах нет, эмбеддинги и реранкер подменяются
через `unittest.mock`.

## Допущения и расхождения

- **Зависимости.** Модуль написан на стандартной библиотеке, хотя регламент
  разрешает `faiss-cpu`, `rank-bm25`, `numpy`, `tiktoken` и другие пакеты из
  `Данные/requirements.txt`. Так решение не зависит от установки пакетов.
  Если скорость или качество потребуют, BM25 меняется на `rank-bm25`, а
  косинус — на `faiss.IndexFlatIP` без изменения внешнего контракта.
- **Индекс в ZIP.** Регламент (раздел 4) прямо запрещает класть в архив
  данные и индексы, поэтому индекс строится на лету. Кэш живёт только в
  памяти процесса: контейнер проверки обычно свежий.
- **Диалоги.** `retrieve` получает готовый поисковый запрос: движок сам
  добавляет прошлые реплики в `build_search_query`. Параметр `context` не
  добавлялся, протокол не менялся.
- **Порог «ничего не найдено».** Отдельного абсолютного порога нет: движок
  уже отбрасывает слабые фрагменты относительно лучшего. Второй порог в RAG
  только дублировал бы логику.
- **Время с реранкером.** Заявленные в задании 3 секунды на `retrieve`
  локально не проверены: прокси доступен только на платформе. Без сети
  поиск занимает меньше миллисекунды, сеть добавляет один вызов эмбеддинга
  и один вызов реранкера.

## Известные ограничения

- BM25 может пропустить перефраз без общих словоформ; плотный канал призван
  уменьшить этот риск, но его качество требует отдельного замера.
- Русская морфология обрабатывается усечением окончаний, а не лемматизацией:
  возможны редкие ложные совпадения.
- Последний точечный прогон использовал BM25 и реальный chat-запрос; embeddings
  и reranking в этом прогоне были отключены. Поддержка этих endpoint на текущем
  OpenRouter-конфиге отдельно не подтверждена.
- Чанкинг проверен на демо-базе; при другой структуре Markdown возможны
  чанки короче 400 символов, если раздел заканчивается таблицей.
