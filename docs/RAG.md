# RAG: поиск по базе знаний EnergyTool

Модуль `rag_engine.py` — гибридный поиск по базе знаний. Вызывается из
`consultant_engine.py` через протокол `Retriever`: объект с методом
`retrieve(query, top_k) -> list[RetrievedChunk]`.

## Место в цепочке

```text
solution.py  ->  consultant_engine.consult()  ->  RagRetriever.retrieve()
                     (промпт, история, отсев)        (чанки + source + score)
```

Подключение — одна строка в `build_default_engine`:

```python
from rag_engine import build_default_retriever

retriever = build_default_retriever()   # вместо KnowledgeBaseSearch.from_path
```

`build_default_retriever()` возвращает `None`, если база не найдена: движок
продолжает работать без контекста и честно отвечает, что данных нет.

## Контракт

Используется `RetrievedChunk` из `consultant_contracts.py` как есть:

```python
@dataclass(frozen=True)
class RetrievedChunk:
    text: str
    source: str
    score: Optional[float] = None
```

`source` — `путь/к/файлу.md > Раздел > Подраздел`, путь относительно корня
`knowledge-base.zip`. Этот же текст движок показывает в режиме отладки веба.

`score` всегда положительный и сравнимый по шкале: движок отбрасывает
фрагменты слабее `0.5 * max(score)`, поэтому плоские скоры (например, чистый
RRF) для него бесполезны.

## Как устроен поиск

1. **Распаковка.** `knowledge-base.zip` ищется в `DATA_DIR` (по умолчанию
   `data`), рядом с модулем и в рабочем каталоге. Распаковка — в `tempfile`,
   с защитой от выхода за пределы каталога. Один раз на процесс.
2. **Чанкинг.** Markdown режется по заголовкам `#`, `##`, `###`; иерархия
   заголовков уходит в `source`. Блок длиннее 3200 символов дробится по
   абзацам с перекрытием, короткие хвосты приклеиваются к соседу. Таблицы и
   списки не разрываются: разрезается только между строками.
3. **BM25.** Своя реализация, без зависимостей. Токенизация: нижний регистр,
   русские стоп-слова, усечение частых окончаний (`-ками`, `-ами`, `-ка`,
   `-ки`, `-ов`, ...). Усечение нужно, чтобы «симки» и «сим-картами» сходились;
   полноценная лемматизация требует pymorphy и лишних зависимостей.
4. **Эмбеддинги (необязательно).** `POST {LLM_BASE_URL}/embeddings` с моделью
   из `EMB_MODEL`, батчами по 32. Векторы нормализуются, косинус считается
   через numpy, если он установлен, иначе чистым Python.
5. **Объединение.** Скоры каналов нормируются и складываются с весами
   0,6 (BM25) и 0,4 (эмбеддинги). Нормировка выбрана вместо RRF, чтобы
   относительный отсев движка работал.
6. **Реранкер (необязательно).** Топ-15 кандидатов уходят в
   `POST {LLM_BASE_URL}/rerank` с моделью из `RERANKER_MODEL`. Логиты
   переводятся сигмоидой в `(0, 1)`; при ошибке или отсутствии модели
   поиск продолжается без реранкера.
7. **Отказ.** Пустой запрос, пустая база, недоступная модель — возвращается
   пустой список, решение принимает движок.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` / `OPENAI_BASE_URL` | адрес прокси организаторов |
| `LLM_API_KEY` / `OPENAI_API_KEY` | служебный ключ, в логи не попадает |
| `EMB_MODEL` | модель эмбеддингов; без неё плотный канал выключен |
| `RERANKER_MODEL` | модель реранкера; без неё реранкер не вызывается |
| `TOP_K` | размер выдачи, по умолчанию 5 |
| `DATA_DIR` | где искать `knowledge-base.zip`, по умолчанию `data` |
| `RAG_DISABLE_DENSE` | `1` — принудительно работать только на BM25 |

`CHUNKER` и `RERANKER_TOP_N` платформа передаёт, но модуль их не использует:
размер чанка задан константами, число фрагментов определяет `TOP_K`, а
реранкер переставляет всех 15 кандидатов. Это осознанное упрощение.

## Потокобезопасность

`consult()` вызывается из нескольких потоков (`MAX_WORKERS`). Индекс
строится ровно один раз под `threading.Lock` (двойная проверка), дальше
`retrieve` только читает. Тест `test_thread_safety_builds_index_once`
проверяет, что при восьми параллельных вызовах база индексируется один раз.

## Замеры на демо-базе

Демо-база: 19 файлов, ~200 КБ Markdown. Разметка на 18 вопросов лежит в
`local-data/retrieval_labels.csv` (каталог в `.gitignore`, материалы
организаторов в репозиторий не попадают).

| Показатель | Значение |
| --- | --- |
| чанков | 121 (средний 1077 символов, максимум 3146) |
| построение индекса (BM25) | 0,03 с на каталоге, 0,2 с на zip |
| один `retrieve` без сети | < 1 мс |

### Сравнение с бейзлайном

Замер `tools/eval_retrieval.py`, top_k = 8, режим без эмбеддингов:

| Retriever | hit@1 | hit@3 | hit@8 | MRR |
| --- | --- | --- | --- | --- |
| `kb_search` (бейзлайн BM25) | 0,67 | 0,89 | 1,00 | 0,79 |
| `rag_engine` (BM25-режим) | 0,72 | 1,00 | 1,00 | 0,83 |

Прирост дают чанкинг по заголовкам, усечение окончаний и нормированные скоры,
а не эмбеддинги: плотный канал в замере был выключен, прокси локально недоступен.

Подбор размера чанка:

| Лимит чанка | Чанков | hit@1 | hit@3 | MRR |
| --- | --- | --- | --- | --- |
| 3200 (текущий) | 121 | 0,72 | 1,00 | 0,83 |
| 2400 | 130 | 0,67 | 0,94 | 0,80 |
| 2000 | 135 | 0,72 | 0,89 | 0,82 |

Текущий размер оставлен: меньше чанков — ровно то же качество при меньшем
контексте для модели.

### Критерии приёмки из задания

- «крыша на два ската — восток и запад» → `20-products/23-solar.md`, раздел
  «Размещение» (скор 0,60);
- «симки другого оператора» → `20-products/22-askue.md`, фрагмент про
  сим-карты других операторов (скор 0,60).

Эти два случая закреплены тестами.

### Как запускать замер

```bash
python3 tools/eval_retrieval.py \
    --questions local-data/demo_questions.csv \
    --labels local-data/retrieval_labels.csv \
    --kb local-data/knowledge-base.zip \
    --retriever rag_engine:from_path
```

`--retriever` принимает `модуль:фабрика`, где фабрика получает путь к базе и
возвращает объект с методом `retrieve`. Поэтому указывается
`rag_engine:from_path`, а не `rag_engine:retrieve`: функция `retrieve` не
принимает путь к базе и не возвращает объект.

## Как запускать тесты

```bash
python -m unittest discover -s tests -p "test_rag.py" -v
```

CI использует `unittest`, а не pytest: `python -m unittest discover -s tests`.
Реальных запросов к прокси в тестах нет, эмбеддинги и реранкер подменяются
через `unittest.mock`.

## Допущения и расхождения

- **Зависимости.** Модуль написан на стандартной библиотеке, хотя регламент
  разрешает `faiss-cpu`, `rank-bm25`, `numpy`, `tiktoken` и другие пакеты из
  `Данные/requirements.txt`. Так решение не зависит от установки пакетов.
  Если скорость или качество потребуют, BM25 меняется на `rank-bm25`, а
  косинус — на `faiss.IndexFlatIP` без изменения внешнего контракта.
- **Индекс в ZIP.** Регламент (раздел 4) прямо запрещает класть в архив
  данные и индексы, поэтому индекс строится на лету. Кэш живёт только в
  памяти процесса: контейнер проверки обычно свежий.
- **Диалоги.** `retrieve` получает готовый поисковый запрос: движок сам
  добавляет прошлые реплики в `build_search_query`. Параметр `context` не
  добавлялся, протокол не менялся.
- **Порог «ничего не найдено».** Отдельного абсолютного порога нет: движок
  уже отбрасывает слабые фрагменты относительно лучшего. Второй порог в RAG
  только дублировал бы логику.
- **Время с реранкером.** Заявленные в задании 3 секунды на `retrieve`
  локально не проверены: прокси доступен только на платформе. Без сети
  поиск занимает меньше миллисекунды, сеть добавляет один вызов эмбеддинга
  и один вызов реранкера.

## Известные ограничения

- BM25 промахивается на перефразах без общих корней: «магазины в одном
  кабинете» не находит раздел про сеть магазинов. Это закрывает плотный канал
  на `bge-m3`, который локально не проверен.
- Русская морфология обрабатывается усечением окончаний, а не лемматизацией:
  возможны редкие ложные совпадения.
- Путь `/rerank` на прокси взят из задания и не проверен живым запросом.
- Чанкинг проверен на демо-базе; при другой структуре Markdown возможны
  чанки короче 400 символов, если раздел заканчивается таблицей.
