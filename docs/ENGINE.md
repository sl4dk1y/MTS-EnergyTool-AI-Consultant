# Consultant Engine

Движок отвечает на вопрос клиента по базе знаний EnergyTool. Его вызывают конкурсный адаптер `solution.py` и, позже, backend веб-прототипа.

## Как проходит запрос

1. `build_search_query` собирает поисковый запрос из последнего вопроса и истории диалога.
2. Retriever возвращает до `TOP_K` фрагментов базы.
3. Если фрагментов нет или поиск упал, модель не вызывается. Движок сразу отвечает, что подтверждённого ответа в материалах нет, и предлагает передать вопрос специалисту.
4. `build_messages` собирает сообщения. В системном только инструкции. Найденные фрагменты идут в последнем сообщении пользователя блоком `<база_знаний>` с пометкой, что это данные, а следом вопрос клиента. Теги блока вырезаются из текста документов, чтобы документ не мог закрыть блок раньше времени. Общий объём фрагментов не больше `MAX_CONTEXT_CHARS`, даже если первый фрагмент длиннее.
5. `LLMClient` получает ответ модели, `clean_answer` вырезает рассуждения `<think>`, служебные префиксы и сноски.
6. Если модель упала или вернула пустой ответ, движок отдаёт запасной ответ и не выбрасывает исключение. Если исключение всё же дошло до `solution.py`, на этот вопрос пишется запасной ответ, остальные ответы сохраняются.

Для веба используется класс `ConsultantEngine(llm, retriever)`, история сессии передаётся в `ConsultantRequest.history`.

## Контракт с RAG

Описан в `consultant_contracts.py` и в issue #52.

- **Запрос.** Его собирает движок. В `retrieve(query, top_k)` приходит готовая строка, RAG её не переписывает и историю сам не разбирает.
- **source.** Строка вида `путь/к/файлу.md > Заголовок > Подзаголовок`, путь относительно корня `knowledge-base.zip`. Показывается в режиме отладки и попадает в `ConsultantResponse.sources`.
- **score.** Любая шкала, больше значит релевантнее. Движок сравнивает score только внутри одной выдачи.
- **Потоки.** `retrieve` вызывается одновременно из `MAX_WORKERS` потоков.
- **Размещение.** Модуль RAG лежит в корне репозитория, потому что конкурсный ZIP не допускает подкаталогов. Движок подключает его сам в `build_retriever`, правки после мержа не нужны.

Если `rag_engine.py` в репозитории нет или он упал при создании, работает временный `kb_search.py`. Это BM25 по разделам Markdown на стандартной библиотеке. Переменная `RETRIEVER=bm25` включает BM25 принудительно, например для сравнения на платформе.

## Порог релевантности

Абсолютный порог зависит от шкалы score и выбирается на стороне RAG (#12). В движке есть относительный фильтр `filter_by_relative_score`. Фрагмент отбрасывается, если его score меньше `RELATIVE_SCORE_CUTOFF` от лучшего в выдаче. Первый фрагмент и фрагменты без score остаются всегда.

По умолчанию фильтр выключен (`RELATIVE_SCORE_CUTOFF=0`), потому что шкала score у основного RAG своя. На демо-вопросах с BM25 и с RAG порог 0.5 не терял нужный файл, но включать его будем только после согласования с RAG и замера на платформе.

## Замер качества поиска

`tools/eval_retrieval.py` прогоняет размеченные вопросы через retriever и считает hit@1, hit@3, hit@k, MRR и среднее число фрагментов после фильтра. LLM не вызывается.

```bash
python3 tools/eval_retrieval.py --questions local-data/demo_questions.csv --labels local-data/retrieval_labels.csv --kb local-data/knowledge-base.zip
```

Разметка это CSV с колонками `id,expected`, где в `expected` через `|` перечислены файлы базы с ответом. Она строится по материалам организаторов, поэтому лежит только в `local-data/`, папка в `.gitignore`. Другой retriever подключается флагом `--retriever модуль:фабрика`. Фабрика принимает путь к базе и возвращает объект с `retrieve`, для основного RAG это `--retriever rag_engine:from_path`.

Результат временного BM25 на 18 демо-вопросах, top_k 8, попаданием считается фрагмент из нужного файла.

| cutoff | hit@1 | hit@3 | hit@8 | MRR | фрагментов |
|---:|---:|---:|---:|---:|---:|
| 0 | 0.67 | 0.89 | 1.00 | 0.79 | 8.0 |
| 0.5 | 0.67 | 0.89 | 1.00 | 0.79 | 6.4 |
| 0.7 | 0.67 | 0.89 | 0.89 | 0.77 | 3.7 |

Разметка грубая, на уровне файла, а не раздела. Набор маленький, цифры годятся для сравнения BM25 и RAG между собой, но не как оценка качества ответов.

## Заявка

`leads.py` готовит заявку менеджеру. Поля ФИО, телефон, название компании и краткое резюме диалога. В конкурсном запуске модуль не используется.

- `prepare_lead(history, llm, form)` собирает черновик. Контакты модель достаёт только из реплик клиента, телефон дополнительно ищется регуляркой. Данные из формы важнее найденных в диалоге. Резюме пишет модель, при её сбое резюме собирается из реплик клиента.
- `validate_lead(fields, summary)` нормализует и проверяет поля. Телефон приводится к `+7XXXXXXXXXX`, ФИО должно состоять из двух-четырёх слов из букв.
- `LeadDraft.missing` содержит пустые и ошибочные поля, `errors` тексты ошибок для формы, `is_complete` готовность к отправке.
- `missing_fields_message(draft)` формулирует, что ещё нужно спросить у клиента.
- `wants_to_leave_request(text)` замечает, что клиент сам просит связаться или оформить заявку, отказ вроде «пока не готов» не считается.

Порядок в вебе такой. Клиент нажимает кнопку или пишет, что хочет заявку. Backend вызывает `prepare_lead` и показывает черновик. Клиент правит поля и подтверждает. Backend сохраняет заявку. Подтверждение и хранение относятся к backend (#30, #31).

В разработке и тестах используются только выдуманные данные.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `RETRIEVER` | пусто | `bm25` включает временный BM25 вместо `rag_engine` |
| `TOP_K` | 8 | Сколько фрагментов запрашивать у retriever |
| `RELATIVE_SCORE_CUTOFF` | 0 | Доля от лучшего score, ниже которой фрагмент отбрасывается, 0 отключает фильтр |
| `LLM_TIMEOUT_SECONDS` | 40 | Таймаут одного запроса к модели, попыток две |
| `MAX_WORKERS` | 4 | Сколько вопросов `solution.py` обрабатывает параллельно |
| `TIME_BUDGET_SECONDS` | 1020 | Через сколько секунд от старта недоделанные вопросы получают запасной ответ |

Адрес, ключ и модель LLM берутся из `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`, как описано в регламенте.
