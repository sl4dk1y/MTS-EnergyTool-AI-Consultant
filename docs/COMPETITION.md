# Конкурсный runtime: подтверждённые требования

Источник этого документа — локально доступный файл `Данные/Технический регламент _ МТС.docx`, предоставленный организаторами. Сам файл и примеры не копируются в публичную документацию. Документ сверялся с оригиналом, находящимся в каталоге `Данные/`; оригинал не включается в публичный репозиторий.

## Подтверждённый контракт

- **Сдача:** команда загружает ZIP-сабмит; платформа запускает его в Docker-контейнере и передаёт ответы LLM-судье.
- **Структура ZIP:** файлы располагаются в корне архива, без внешней папки. Обязательны `solution.py` и `requirements.txt`; дополнительные корневые `.py`-модули допустимы, если импорты работают в окружении.
- **Вход:** `questions.csv` в UTF-8 с колонками `id` и `question`; платформа передаёт его исполняемому скрипту. Каждая строка — независимый кейс. Если вопрос содержит историю, ответ формируется на последнюю реплику с учётом этой истории; состояние между разными ID не переносится.
- **База знаний:** `knowledge-base.zip` передаётся платформой отдельно. В ZIP-сабмит входные файлы включать не нужно.
- **Выход:** `solution.py` самостоятельно создаёт в рабочем каталоге `submission.csv`, UTF-8, ровно две колонки `id,answer`. Для каждого входного ID обязателен один непустой ответ; ID не повторяются, дополнительных колонок нет. CSV должен корректно экранировать запятые, кавычки и переводы строк.
- **Длина ответа:** максимум 10 000 символов на ответ; рекомендовано до 150 слов, но более подробный ответ допустим, когда этого требует вопрос.
- **Модель и API:** используется единая генеративная модель **Qwen3.8-27B**; её идентификатор передаётся через окружение. Вызов генерации направляется на `{LLM_BASE_URL}/chat/completions`, заголовок `Authorization: Bearer {LLM_API_KEY}`. Платформа автоматически передаёт адрес и служебный ключ локального OpenAI-совместимого прокси.
- **Переменные окружения:** адрес — `LLM_BASE_URL` или `OPENAI_BASE_URL`; ключ — `LLM_API_KEY` или `OPENAI_API_KEY`; модель — `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL`. Также доступны `DATA_DIR` (по умолчанию `data`), `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `TOP_K`, `CHUNKER`, `EMB_MODEL`, `RERANKER_MODEL`, `RERANKER_TOP_N`, `PYTHONPATH`.
- **Поиск и модели:** команда реализует собственный поиск и обработку базы. Для embeddings доступна **BAAI/bge-m3**, для reranking — **Qwen3 Reranker 8B** (необязательно); используется тот же прокси и доступ.
- **Зависимости и файлы:** зависимости устанавливает платформа; `pip install` из `solution.py` запрещён. `requirements.txt` содержит зависимости разрешённого набора с зафиксированными версиями. Не включать в ZIP файлы данных, индексы, конфигурации и `.whl`.
- **Ресурсы:** до 8 CPU, 16 ГБ RAM, до 20 минут на запуск; превышение времени приводит к тайм-ауту.
- **Лимит отправок:** 5 сабмитов в день на команду, сброс в 00:00 МСК; максимальный размер ZIP — 128 МБ.
- **Требуемое поведение:** отвечать по материалам базы, задавать уточняющие вопросы при недостатке данных и корректно отказывать, если информации нет.

## Автоматическая оценка

LLM-судья сравнивает ответ команды с baseline с опорой на утверждённый golden-ответ. Каждый вопрос сравнивается в двух порядках: baseline/команда и команда/baseline. В каждом раунде используется шкала 0; 0,25; 0,5; 0,75; 1. Итог вопроса — среднее двух оценок.

- **Match Rate** — средний балл по успешно оценённым вопросам.
- **Win Rate** — доля побед среди побед и поражений; ничьи не учитываются. Если все сравнения — ничьи, значение равно 0,5.
- **Score** = `0,7 × Match Rate + 0,3 × Win Rate`.

Публичный лидерборд рассчитывается на public-подмножестве, окончательная автоматическая оценка — на private-подмножестве; состав, golden-ответы и baseline участникам не раскрываются.

## Этапы, экспертная оценка и допуск

Кейс описывает два этапа:

1. **Онлайн-этап:** ZIP-сабмиты проходят автоматическую оценку LLM-судьёй. Итог онлайн-этапа складывается из оценки LLM-судьи (50%) и экспертной оценки решения (50%); перед суммированием оценки приводятся к единой шкале.
2. **Финал:** итоговая оценка состоит из результата онлайн-этапа (40%) и оценки финальной защиты (60%).

Экспертная оценка онлайн-этапа (0–5 баллов за критерий):

| Вес | Критерий |
|---:|---|
| 30% | Работоспособность |
| 25% | Качество консультации |
| 15% | Скорость и стабильность |
| 15% | Архитектура |
| 10% | Безопасность, зависимости и документация |
| 5% | Качество презентации |

К финальной экспертной оценке допускаются решения, которые получили больше 0 баллов от LLM-судьи, имеют работающий веб-интерфейс и полный комплект материалов. Команда не допускается, если сабмит получил 0 баллов от LLM-судьи, чат-интерфейс отсутствует/не запускается/не позволяет пройти основной сценарий консультации от первого вопроса до заявки либо отсутствуют обязательные материалы финальной сдачи. Незначительные недочёты интерфейса, не мешающие основному сценарию, учитываются в критерии «Работоспособность».

Экспертная оценка финала (0–5 баллов за критерий):

| Вес | Критерий |
|---:|---|
| 25% | Ценность для клиента и бизнеса |
| 25% | Качество бота |
| 20% | Обоснованность технических решений |
| 15% | Сценарий внедрения |
| 10% | Качество защиты и ответов на вопросы |
| 5% | Командное владение решением |

## Материалы финальной сдачи

В конце хакатона команда загружает на платформу один из двух вариантов:

### Вариант A: PDF-презентация

- В презентации должен быть указан порядок проверки и ссылка на репозиторий на первом слайде.
- Если репозиторий приватный, предоставить доступ аккаунту жюри `hack-and-change-2026`.
- Если есть развёрнутый интерфейс, добавить ссылку на него.
- Описать проблему и пользователя, архитектуру, сценарий консультации, примеры работы, ограничения и идеи развития.
- Все файлы решения должны быть доступны в репозитории.

### Вариант B: ZIP-архив

Архив должен включать:

- исходный код работающего решения;
- `README.md` с назначением и архитектурой, одной командой запуска через Docker, переменными окружения, портами, зависимостями, порядком проверки основного сценария и известными ограничениями;
- `Dockerfile`, `compose.yaml` и `.dockerignore` для запуска всех компонентов одной командой;
- файл зависимостей с зафиксированными версиями (`requirements.txt`, `package-lock.json` или аналог);
- `.env.example` без действующих ключей и паролей.

Если используются внешние API, README должен описывать сервис, модель, имя переменной окружения и порядок подключения ключа. Рабочие секреты нельзя включать ни в один материал сдачи.

- [ ] В корне архива находятся `solution.py`, `requirements.txt` и только необходимые дополнительные корневые `.py`-модули.
- [ ] Нет внешней папки-обёртки, данных, базы знаний, индексов, конфигураций и `.whl`.
- [ ] Зависимости разрешены, версии зафиксированы; скрипт не запускает `pip install`.
- [ ] Скрипт читает переданные платформой вопросы и базу, использует пути/переменные из окружения.
- [ ] API-запрос использует прокси, переданный платформой; значения ключей не зашиты в код и не логируются.
- [ ] `submission.csv` создаётся в рабочем каталоге, UTF-8, с заголовком `id,answer` и ровно двумя колонками.
- [ ] Каждый входной ID представлен ровно один раз непустым ответом; CSV-экранирование корректно.
- [ ] Ответы не превышают 10 000 символов; нет переноса состояния между ID.
- [ ] Решение задаёт уточнение при нехватке вводных и не выдумывает сведения вне базы.
- [ ] Архив не превышает 128 МБ и проверен на запуск в заданных ресурсах и лимите времени.
- [ ] Учтён лимит пяти отправок в день на команду.
